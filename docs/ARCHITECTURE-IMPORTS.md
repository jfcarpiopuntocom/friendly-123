# ARCHITECTURE-IMPORTS · friendly-123

**Fecha de contraste:** 2026-11-01. **Naturaleza:** mapa de precedentes y decisiones técnicas; **documentación solamente**. No importa código ni cambia la aplicación, el protocolo, los permisos, la licencia o el despliegue.

## Principio de terminación

Aprovechar **patrones ya documentados** y el código existente de friendly-123; mantener Yjs, el modelo local-first y los movimientos causales sin reescribir el motor. Una referencia externa **no demuestra** que la implementación local cumpla el patrón. Cualquier cambio en el shell activo requiere pruebas, presupuestos, compatibilidad entre versiones, censo de dispositivos y autorización de lanzamiento.

## Contratos para agentes — antes de escribir más sincronización

1. **Revisar el camino activo:** `docs/index.html` → sesión/autenticación → `peer-sync.js` / `sync-yjs.js` → transporte efectivamente cargado → ACK y almacenamiento → reabrir en otro navegador/PWA. Ningún módulo existente pero no importado cuenta como funcional.
2. **C-02 no es «cerrado» por pasar 4 unitarios.** Probar los 50.541 sobres / 410 MB en copia estrictamente aislada, interrupción y recomposición, sin pérdida/duplicación ni borrado hasta ACK confirmado. **No abrir clones de perfiles reales conectados.**
3. **C-03 mantiene dos épocas incompatibles** hasta demostrar identidad del contador y descendencia causal; el evento físico observado no es una corrección derivada de otra pantalla. Conservar los hechos de ventas y fotos.
4. **C-01 necesita almacenamiento duradero activo** si la aceptación exige abrir un aparato días después de apagar otro. Un fallback P2P↔relay que sólo vive durante la conexión no cubre por sí solo el caso.
5. **C-07 mantiene el orden aprobado:** censo de aparatos/PIN vigentes de clientes sin alterarlos; administración desde panel JFC, después cambios coordinados. Ninguna clave derivada se activa sobre clientes reales sin migración y recuperación ensayadas.
6. **Versión y revisión:** one-file-one-owner, PR Draft independiente, ningún sellado de shell en feature; CI sobre SHA final, Opus revisa y JFC autoriza. El plan externo no autoriza desactivar gates ni relajar tests.
7. **Presupuesto:** medir bytes de datos/ops/fotos, ACK, egress y retención **antes** de activar Cloudflare o Supabase para toda la cohorte. No reintroducir el incidente de cuota.

## Componentes deliberadamente no adoptados ahora

- **Loro, Automerge, Electric, Replicache/Zero, PowerSync y RxDB como motores nuevos:** introducirían sustitución/migración del camino activo cuando aún hay divergencia de datos. No se rechazan por ideología; se posponen por riesgo de cambio y esfuerzo de validación. Licencias y modelo comercial de cada distribución se revisan individualmente antes de cualquier copia de código.
- **Código de repositorios de ejemplo:** este documento **atribuye ideas y documentación**, no afirma haber copiado fuentes ni usa sus licencias como permiso para incorporar dependencias sin revisión.
- **Promesa de “un script tag = app reparada”:** falta prueba de autenticación, cursorización y ACK de extremo a extremo, cuota, bootstrap del PIN y compatibilidad PWA/URL/cliente de shell antiguo.
